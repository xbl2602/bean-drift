# Landing-page-v2 terrain assets

Real lunar south-pole terrain derived from the LOLA 10 m DEM crop used by `prototypes/lunar-scene-demo`.
Everything in this directory is generated from those source files; nothing here is hand-painted or synthetic.
All assets are 640×640, every file is < 2 MB, and all of them are re-generated by one script (`tools/build_assets.py`).

## Source inputs (read-only, never modified)

| file | what it is |
|---|---|
| `prototypes/lunar-scene-demo/data/derived/dem_crop.i16` | 4200×4200 int16 **little-endian**, row-major, DN values; metres = DN × `scale` |
| `prototypes/lunar-scene-demo/data/derived/dem_meta.json` | `n=4200, px=10.0, x0=-21005, z0=-21005, scale=0.5, sunAz=62, sunEl=1.5, pole_height_m=1293, min_m=-2872.5, max_m=1998` |
| `prototypes/lunar-scene-demo/data/derived/sky_year.json` | 8760 hourly Sun/Earth az+el samples for 365 d from `2026-11-01T00:00:00Z` (at the pole) |

Conventions were taken from `prototypes/lunar-scene-demo/demgrid.js` and `lola.js` (not guessed):

* `lola.js` → `createDemGrid({data: raw, nx, nz, px, x0, z0, scale})` → **height = DN × 0.5**, read as `Int16Array` from the little-endian file;
* `demgrid.js` header → pixel `(i, j)` is **centred** at `x = x0 + i*px`, `z = z0 + j*px`; `x` runs along columns, `z` along rows (image down); heights are metres above the 1737.4 km reference sphere;
* azimuth convention (from `demgrid.js`/`ephemeris.js`): **0° = north = −z, 90° = east = +x**; elevation positive up;
* `horizonProfile()` computes `atan2(h(d) − (h0 + eye) − d²/(2R), d)` with `R = 1737400 m`; the same formula (curvature drop included) is used here.

DEM crop extent: 4200 × 10 m = **42 000 m × 42 000 m** (x, z ∈ [−21 010, +20 990] m); the lunar south pole is at (0, 0).

## Python used

```
Python 3.12  ·  numpy 2.3.5  ·  Pillow 12.3.0   (no scipy)
```

Any recent Python 3 with numpy and Pillow works; all numbers below were produced with the versions listed above.

`terrain-meta.json` (exact values):

```json
{"size": 640, "spacingM": 65.625, "minM": -2871.0, "maxM": 1959.0,
 "sunAzDeg": 62.0, "sunElDeg": 1.5, "x0": -20977.1875, "z0": -20977.1875, "poleHeightM": 1293.0}
```

Notes on the meta:

* `spacingM = 42000 / 640 = 65.625 m`; `x0`/`z0` are the **world coordinates of the centre of pixel (0,0)** — the same
  pixel-centre convention as `demgrid.js`. The grid therefore covers exactly x, z ∈ [−21010, 20990] m, i.e. the full
  42 km crop (edges at `x0 − spacingM/2` and `x0 + (size − 0.5)·spacingM`).
* `minM`/`maxM` are the actual min/max of `terrain.bin` (checked in the acceptance step). The full-resolution DEM is
  −2872.5 / 1998 m; area-averaging to 65.625 m cells loses the extreme single pixels, hence −2871.0 / 1959.0.
* `poleHeightM = 1293.0` is the full-resolution DEM height at the pole (`dem_meta.json: pole_height_m`); a bilinear
  sample of the 640 grid at (0, 0) gives 1292.1 m, i.e. the smoothing changed it by < 1 m.

## Methods

### 1. Downsampling 4200 → 640 (`terrain.bin`)
Ratio 4200/640 = 6.5625 is not an integer, so instead of dropping pixels every 6.5625 columns (which would bias the
grid) the script does an **exact area-weighted mean** over the full image extent, using the analytic integral of the
piecewise-constant DEM (`blocksum()` in the script). Each 640-grid cell is the true mean of the 65.625 m × 65.625 m
area it covers, and no strip at the crop edge is lost. Heights are then rounded to the nearest metre for the int16
file; `minM`/`maxM` are taken from that rounded file.

### 2. Slope and hillshade
* Gradients from `numpy.gradient` on the 640 grid with `spacingM = 65.625 m` (central differences): `dx = ∂h/∂x`,
  `dz = ∂h/∂z` in m/m. Slope = `degrees(atan(hypot(dx, dz)))`.
  Slope statistics (degrees): p50 = 11.2, p90 = 29.6, p99 = 33.4, **max = 38.41** (the value `slope-gray.png` maps to 255).
* `slope.png` colour ramp saturates at 45° (paler → red; see `SLOPE_STOPS` in the script); `slope-gray.png` is the
  **linear** 0…38.41° → 0…255 map without any clamp other than 0…1.
* `height.png` / `height-gray.png`: linear normalisation `t = (h − minM) / (maxM − minM)`; the colour ramp is
  deep teal-black → teal → olive → amber → warm white; the grey file is exactly `round(t·255)`.
* Hillshade: surface normal `n = (−dx, 1, −dz)/|…|` (world frame x right, y up, z image-down) and the real Sun
  direction `s = (sin az·cos el, sin el, −cos az·cos el)` from the meta (az 62°, el 1.5°), so
  `cos_i = n·s`. Display value = `255 · clip(0.08 + 0.92·clip(cos_i,0,1)^0.55, 0, 1)`; the ambient + gamma only
  make the 1.5° grazing sun legible on a card — the direction and the illumination term are physical, the tone
  mapping is not radiometric. No cast shadows are baked into this layer (the demo's `shadow.png` is a separate,
  ray-cast product).

### 3. Horizon profiles (`horizon-*.json`, full 4200×4200 DEM)
Bilinear sampling of the full-resolution DEM (10 m posts), a **10 m ray step from 10 m out to 14 km** (the same 14 km
cap as the scene's `horizonProfile`), eye height **1.6 m** (same as `common.js` `EYE`), and the lunar curvature drop
`d²/(2R)` exactly as in `demgrid.js`:

```
elevation(az) = max over d of  atan2( h(x + d·sin az, z − d·cos az) − (h0 + 1.6) − d²/(2·1737400), d )
```

Both points were chosen so that every 14 km ray stays **inside** the 42 km crop, so no edge clamping enters these files.

| file | point (x, z) m | height | lat / lon (polar approx.) | horizon min / **max** | max at az |
|---|---|---|---|---|---|
| `horizon-highland.json` | (−2755.0, 6245.0) | 1736.5 m | −89.7749° / 203.8048° | −3.77° / **+1.05°** | 235.0° |
| `horizon-basin.json` | (6716.6, 4419.7) | −2804.6 m | −89.7348° / 123.3460° | +16.64° / **+28.70°** | 332.5° |

* **highland** = high ground near the region centre. It is a local summit at 1736.5 m, among the highest points of
  the whole 42 km crop; from a summit the terrain horizon lies below eye level in nearly every direction
  (mean −1.48°), so the *maximum* occlusion angle is only 1.05° — that is the correct physical answer, not a
  missing ray step. The sun is above this horizon **81.3 %** of the year, the Earth **45.8 %**.
  (The absolute highest point within 9 km, 1739.5 m at (−2655, 6075), looks down −10.7° into Shackleton crater, so it
  would break the page's [−5°, 30°] sanity range; it was therefore rejected by the picker and this point, 1.4 km away
  on the same ridge, was used.)
* **basin** = low, heavily terrain-occluded point: the lowest Sun-visibility cell (0.000) of the 128×128 scan with a
  ≥ 14 km margin to the crop edge, on the Shackleton crater floor at −2804.6 m. The crater walls stand 16.6°–28.7°
  above the local horizon, so the Sun and the Earth are **never** visible there during the sampled year (0.000 / 0.000).
  This is the deliberate contrast point: same DEM, same algorithm, very different sky.

Independently re-checked the ray march with 5 m, 10 m and 25 m steps and to 21 km: basin max = 28.55–28.70°, highland
max = 1.05° (identical azimuths), so the step size is not the limiting factor. Without the curvature term the values
shift by < 0.2°.

JSON fields: `name`, `description`, `point {xM, zM, latDeg, lonDeg, heightM}`, `azimuthDeg` (144 values,
0…357.5 step 2.5), `elevationDeg` (144 values, degrees, positive above the local horizontal), `sunAzDeg`,
`sunElDeg`, `eyeM`, `curvatureCorrection`, `source`.

### 4. One-year Sun / Earth visibility maps
Computed **on the full-resolution DEM** at 128×128 sample points evenly spread over the 42 km crop, then upscaled
640 with bicubic interpolation (no extra structure invented):

1. for each of the 128×128 points: terrain horizon at **72 azimuths (5° steps)** with the same 10 m→14 km ray march,
   20 m → 14 km geometric distance samples, curvature and 1.6 m eye height;
2. for each of the **8760 hourly** `sky_year.json` samples: the body is visible if
   `el_local > horizon(az)` where the horizon is linearly interpolated between the 5° azimuth bins and
   `el_local = el_pole + degrees((sin az·X − cos az·Z) / R)` is the plane-parallel elevation correction for the
   observer's offset (X, Z) from the pole (same first-order correction as `tools/find_spot.py`);
3. fraction = visible hours / 8760. Colour: black = 0, amber (Sun) / pale cyan (Earth) = 1.

Measured ranges over the map:

| map | min | mean | max | p10 / p50 / p90 |
|---|---|---|---|---|
| Sun | 0.000 | 0.229 | 0.828 | 0.00 / 0.24 / 0.40 |
| Earth | 0.000 | 0.334 | 0.965 | 0.00 / 0.41 / 0.67 |

Sanity anchors against the demo's own published numbers (`lola.js` comments / `find_spot.py`): pole ≈ Sun 32 %, Earth
16 % — this build gives 0.32 / 0.17 at the exact pole with the same ray-march settings; the demo's spot a
(7895, −4105) is documented as Sun 72 %, Earth 79 % — this build gives 0.70 / 0.77 (the 5°-azimuth / 328 m-grid
version gives 0.62 / 0.63 at the nearest grid point). So the method reproduces `find_spot.py` to within ~2 points.

### 5. Latitude / longitude (polar approximation)
For a point (x, z) in metres from the pole, with `r = hypot(x, z)` and `R = 1737400 m`:

```
latDeg = −90 + degrees(r / R)          # south pole: colatitude = ground distance / R
lonDeg = degrees(atan2(x, −z)) mod 360 # az 0 = lon 0, +x = lon 90°E (same convention as ephemeris.js)
```

This is a tangent-plane (gnomonic-like) polar approximation: first order exact on a sphere, with a relative error of
order `(r/R)²/6` in the arc (≈ 6·10⁻⁶ at r = 11 km, i.e. < 10⁻⁴ deg). No lunar ellipsoid/geoid correction.

## Approximations / assumptions (honest list)

1. **Shared sky**: all 8760 Sun/Earth directions come from `sky_year.json`, which was computed for the pole. Across
   the 42 km crop the parallax/direction change is far below 0.1°, so the same azimuth/elevation series is reused;
   the observer's height/offset is only applied through the first-order tangent-plane term `(u·r)/R` (≤ 0.4°).
2. **Point sources**: Sun and Earth are treated as point directions — the solar disk (~0.5°) and the Earth's angular
   radius are not added to the horizon test, and there is no lunar atmosphere (no refraction/extinction). A body is
   "visible" when its elevation is strictly above the terrain horizon.
3. **One year only**: `sky_year.json` covers 2026-11-01 + 365 d (8760 h). That year is used as representative of the
   illumination statistics; the lunar seasonal cycle (±1.5° subsolar latitude) is contained in it.
4. **Outside the crop**: the bilinear sampler repeats the nearest edge pixel beyond the 42 km crop (exactly what the
   scene's `demgrid.sample` does). The two horizon points were chosen with a 14 km edge margin so their JSONs are
   unaffected; the 128×128 visibility map does inherit this approximation near the crop borders, and its outermost
   cells should be treated as indicative only.
5. **Downsampled terrain**: `terrain.bin` is an area mean, not a real 65.6 m DEM; small craters are smoothed. The
   extrema differ slightly from the full-res DEM (−2871/1959 vs −2872.5/1998 m).
6. **Slope baseline**: slope/curvature come from 65.625 m cells, so slopes are averaged over that baseline (a 65.6 m
   mean slope, not the 10 m-pixel slope). The actual maximum is 38.41°.
7. **Hillshade tone mapping**: the ambient term (0.08) and gamma (0.55) are a display choice to make the 1.5° grazing
   Sun readable; the normal, the Sun vector and the `n·s` illumination are physical. No cast shadows in this layer.
8. **Horizon JSON** uses 2.5° azimuth bins, so a very narrow (sub-2.5°) ridge could in principle be missed between
   bins; the elevation values are per-bin maxima and are smooth at that resolution.
9. **Visibility maps** are 128×128 (328 m cells) with 5° azimuth bins — blocky by construction, then upscaled 640 with
   bicubic interpolation purely for display. Fine local shadowing below ~330 m is not resolved, so values are
   approximate (± a few percent); the pattern (crater interiors dark, ridges bright) is the reliable part.

## Rerun

```powershell
# 1) everything (≈ 25 s): terrain + layers + grayscale maps + visibility + horizon + acceptance checks
python prototypes/landing-page-v2/assets/tools/build_assets.py

# individual stages
… tools\build_assets.py --stage base      # terrain.bin, meta, hillshade, height/slope (+ gray)
… tools\build_assets.py --stage vis       # sun/earth visibility maps (≈ 20 s)
… tools\build_assets.py --stage horizon   # horizon JSONs (recomputes vis for the point picker if run alone)
… tools\build_assets.py --stage verify    # checks only, exits non-zero on failure
```

The script resolves paths from its own location (`…/landing-page-v2/assets/tools/build_assets.py`), so it can be run
from any working directory. It only writes into `prototypes/landing-page-v2/assets/`, never into the demo directory,
and makes no git operations.

Acceptance checks built into `--stage verify` (all pass):

* `terrain.bin` has 640×640 = 409 600 int16 samples; its min/max equal `minM`/`maxM`;
* `spacingM · size = 42 000 m` exactly;
* every PNG opens in Pillow at 640×640 (RGB for colour maps, `L` for the grey ones; JPEG `L` for hillshade);
* `height-gray.png` spans exactly 0…255 and equals the linear map of `terrain.bin` over [minM, maxM];
  `slope-gray.png` max = 255 and equals the linear map of the DEM-gradient slope (0…38.41°);
* both horizon files have 144 azimuth samples with a 2.5° step, elevations inside [−5°, 30°], non-constant
  (std 1.13° / 4.17°), and all required `point` keys;
* every file is < 2 MB.
