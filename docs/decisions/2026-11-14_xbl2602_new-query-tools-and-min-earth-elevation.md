# 新增三个查询工具、"同时可见"统计、地球最低仰角（选填）

- **提出人**：`xbl2602`
- **状态**：采纳（接口已实现并验证；"关键日期"和最低仰角的默认值仍没定，见"还没定的"）

## 决定了什么

1. **单点查询加 `yearStats.bothVisibleFraction`**：一年里太阳和地球**同时**可见的时间占比。整月地图里早就有同名的一层（`bothFraction`），点位接口里没有；选址要两者都满足，缺了它前端和 AI 都得自己拼。
2. **地球最低仰角作为选填输入 `minEarthElevationDeg`**（0~60 度）：点位、对比、时间序列、跨日期对比都接受。**不传 = 只看地形**，和之前以及整月地图完全一致；返回里的 `assumptions` 写明用了什么。**不设默认值**：调研没有查到官方阈值（`docs/research/` 里"直连通信的物理判据"那一条仍是未完成）。
3. **三个新的只读工具**（REST 和 MCP 同一份业务代码）：
   - `get_point_timeline` / `GET /api/timeline`：一个点一段时间（最长 31 天）里太阳和地球的曲线、可见时间段（太阳、地球、两者同时）。
   - `compare_dates` / `POST /api/compare-dates`：同一批点在几个时刻的对比（`compare_points` 是多个点、同一时刻，两者互补）。
   - `find_sites` / `POST /api/find-sites`：按坡度、日照比例、通信比例、最长断电/断信号、经纬度框，在整个月面找位置。
4. 顺手把 `get_point_conditions` 过期的工具说明改了（原来写着地形、可见性、一年统计"还没算"，其实已有真实数据）。
5. 字段表、参数、实测大小写在 `docs/SHARED_INTERFACES.md` 2.5、2.5.2、3、3.1~3.3、4，**以那里为准**。

## 为什么

- FEATURE_SPEC 第 8 节自己举的 agent 例子（"找出一年里最长断电不超过 50 小时的平坦位置"）在此之前做不到；题面还要求"对比着陆点和日期"和"展示一个月昼内的变化"，也缺对应的接口。
- 最低仰角：直连通信实际要求地球高过某个角度，只看"露出地平线"会偏乐观。做成选填输入而不是改默认口径，是因为默认口径要和整月地图保持一致（地图是预计算的，改口径要重算）。

## 备选方案

- 把 `compare_points` 的 `time` 改成数组来对比日期：没选。会改变现有返回结构；而且同一个点的地形、一年统计与时间无关，每个时刻都完整返回太浪费（实测 5 点 × 8 时刻约 16 KB，完整结构约 280 KB，远超 AI 窗口单个工具结果 64 KB 的上限）。
- 最低仰角按地球**圆心**算：没选。和现有"圆盘上缘露出即可见"的规则混用两种口径，说不清；选了"上缘高于 max(地形地平线, 最低仰角)"，一条规则统一。代价：比按圆心算的结果略偏乐观（地球视半径约 1°）。
- 最低仰角默认设为 0：不行。地形地平线可以是负的（比光滑球面的水平线还低，实测有 −1.14°），传 0 会改变原有结果，所以"不传"和"传 0"是两件事。
- 整月最低仰角也预计算一套：没做，要重跑流水线；`find_sites` 因此**不带**这个要求，在说明里写明（对通信偏乐观）。

## 还没定的

- **"关键日期"**：见 FEATURE_SPEC 第 1、4 节和 `docs/meetings/offline-meeting-1_mindmap.md` 第 6 步。原件是手写导图，转写只有"显示关键日期"几个字，没有定义，所以没做成字段。现有的 `visibility.<sun/earth>.nextRiseUtc` / `nextSetUtc`、`yearStats` 的可见窗口、时间序列的窗口已经能回答大部分"什么时候有光、什么时候能通信"。
- 最低仰角的合理取值（和用什么天线、什么链路有关）。
- 整月地图是否也要支持最低仰角。

## 影响

- 返回结构只**新增**字段（`yearStats.bothVisibleFraction`、`assumptions`），旧字段一个没变（实测与改动前的输出逐项一致）。
- **自然语言窗口还用不到新工具**：agent 有自己的白名单（`src/features/agent-search/logic/run-agent.ts`，`louis068` 的目录），需要他加。（他系统提示里"null 表示不可用"的过期措辞已由 PR #8 改对。）另外：`compare_points` 满 10 个点已是 64,938 字节，加上最低仰角后 68,942 字节，超过 agent 单个工具结果 65,536 字节的上限，建议他把 agent 能传的点数限制在 8 个以内。
- **`next.config.ts` 改了**：三个新路由要在"打包哪些数据文件"那张表里登记，否则本地能跑、部署到 Vercel 后可能找不到文件。`find_sites` 还要读一年统计文件 `stats-4ppd.u16`（之前注释明确写"API 不读，不打包"，现在不成立了），所以 `/api/find-sites`、`/mcp`、`/api/agent` 要带上它，函数包各多约 14.5 MB（总数据约 55 MB，远小于 Vercel 的 250 MB 上限）。**已验证**：本机在工作目录里跑不了 Turbopack（它不接受指向别处的 node_modules 链接），但 PR #9 的 Vercel 预览部署（Turbopack 构建、真实无服务器函数）上，找位置、时间曲线、跨日期对比、带最低仰角的点位查询、MCP 都返回 200，数字与本机逐项一致（找位置第一名同为 −88.625°、−68.125°，同时可见 0.4765），说明数据文件（含 `stats-4ppd.u16`）都带上了。
- `find_sites` 每次请求读约 19 MB 文件现筛（0.2~0.4 秒）。流量大时可以考虑缓存，但服务端不放可变模块级状态（AGENTS.md 5.3），所以现在没缓存。
- 数据局限没变，反而更显眼了：0.25° 格子会抹平很小的"常亮峰"，当前数据里南纬 80° 以南最长断电最短的格子约 215 小时；想找"几乎常亮"的点，需要更细的数据（TODO Q5）。
