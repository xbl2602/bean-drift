# 点位参数接口：先留槽位，数据后接入

- **提出人**：`xbl2602`
- **状态**：采纳（接口形状已定；个别字段的精确定义见"还没定的"）

## 决定了什么

把 `PointConditions`（`GET /api/point`、MCP `get_point_conditions`、`POST /api/compare` 的返回）扩成"完整字段清单"：

- 新增真实数据：`sun.distanceKm`、`sun.angularRadiusDeg`（星历已能算，处理地形部分遮挡时要用）。
- 新增**占位字段组**，没有数据时值为 `null`：`terrain`（高度、坡度、坡向、地平线剖面、分辨率）、`visibility`（地形遮挡后太阳和地球的圆盘可见比例、下次升起、下次落下）、`yearStats`（一年可见比例、最长断电或断信号、可见窗口）。
- 每一组永远存在，不再是整组 `null`；数据是否接入看 `provenance.<组>.status`。
- 完整字段表（含单位、状态）写在 `docs/SHARED_INTERFACES.md` 第 2 节，**以那里为准**。

## 为什么

前端（product page 的参数卡）、API、MCP、agent 要同时对着一份字段清单开发。数据（LOLA 衍生数据、一年统计）要晚一些才有，但调用方不应该等数据，也不应该等接入后再改代码。

槽位的每个字段都能在 FEATURE_SPEC 第 2、4、6 节找到出处（参数卡的高度、坡度、坡向、地平线剖面、距日落时间、一年日照和地球可见比例、最长断电和断信号、月昼窗口、部分遮挡、来自多少米/像素的数据）。

## 备选方案

- 整组保持 `null`、数据来了再定结构：调用方看不到将来有哪些字段，前端无法提前对接。没选。
- 现在就写全部候选字段（包括 L6、L7、关键日期）：这些的定义没定，字段名都会猜错。没选，见下。
